** TODO Bot-crawlable public pages                    :backend:frontend:
:PROPERTIES:
:CREATED: [2026-10-20 Tue]
:END:
Public (guest-readable) apps are invisible to non-browser consumers: guest login is a frontend ritual (=guest-auto= posts =/api/login= and holds tokens in the browser), so crawlers, link-preview unfurlers, and RSS readers get 401s from the API — and a cold fetch of any URL returns the empty SPA shell, so search engines and unfurls see no content at all. For guest-readable types, serve server-rendered read-only pages at e.g. =/p/<type>/<identity>= (the native blog-engine shape — every real blog serves HTML at the article URL; the SPA stays the editing surface). The anonymous read path (no-credential requests read as the seeded guest; reads only) then survives only as an API-consumer concern — separate decision.
- Crawler glue: canonical tags on the SPA record views pointing at the public URL; a generated =sitemap.xml=; a copy-link button shares the public URL so unfurlers fetch real HTML.
- The public pages are a *materialized build product*, not a per-page cache: a render cycle walks every guest-readable type and renders the list view per type plus the view-mode page per record, into a temp tree that atomically swaps into place (never update in place — a deleted or gone-private record must not leave stale HTML being served). - Serving is static-file cheap: no DB touch, no permission evaluation at request time; =ETag= / =Cache-Control= headers keep bots and unfurlers cheap. Full re-render per change batch is right at Data UI scale (tens to hundreds of records; a pass is milliseconds) — incremental rendering is a non-goal.
