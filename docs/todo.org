** DONE Hook registry (parameterized, data-only)          :compiler:backend:

:CREATED: [2026-08-09 Sun]
:COMPLETED: [2026-08-09 Sun]
:END:
Implement the curated hook registry so models can attach behavior as
pure data: =(:keyword args...)=. Generalizes the current
=*validation-map*= (keyword → function only).

Entry shape: name + parameter schema + factory. Factory closes over
parameters and returns a contract-conforming closure.

Two contracts, one registry concept:
- Validation: =(lambda (type-key field-key value user) -> nil | error-string)=
- Lifecycle:  =(lambda (type-key data user &key roles) -> effect)=
  (e.g. =:post-create=, =:pre-delete=, =:create= overrides)

Surface forms at every hook site (same as README):
- =(:keyword args...)= — registry entry (AI / no-code / hosted)
- =(:shell "script" args...)= — compiler-generated adapter
- =(lambda ...)= — raw Lisp (expert / self-host only)

MVP first slice: validation path (=compile-validations= accepts
parameterized forms). Seed entries needed soon: =:max-length=,
=:in-range= (ratings 1–5), and keep existing keyword entries
(=:required=, =:email=, …) as zero-arg registry entries.

Do not name this "validation registry" or "function registry" —
lifecycle hooks use the same mechanism. Name: *hook registry*.

** DONE Deploy Model action hangs: child processes grab TTY on stdin
:PROPERTIES:
:CREATED: [2026-08-09 Sun]
:COMPLETED: [2026-08-09 Sun]
:END:
Fixed across two sessions. Three distinct bugs were found and fixed:

*** Bug 1: TTY grab (fixed in prior session)
=:input nil= added to all three =uiop:run-program= calls in
=lisp/model.lisp= so child processes get EOF instead of blocking
on =/dev/tty=.

*** Bug 2: Model file written without quote prefix
=deploy-model-write-file= in =lisp/model.lisp= wrote the model
plist via =(prin1 model-plist s)= — producing =(:title ...)=
without the leading ='=. But every consumer in the deploy pipeline
(=top-level-model-field=, =set-model=, =compile_default_model=)
expects a quoted plist ='(:title ...)= and uses =(cadr (read in))=
to strip the quote. Without the quote, =(cadr (read in))= returns
the first value in the plist (e.g. ="To Do List"=) instead of the
plist itself, causing =get_model_field= to fail silently.

Fix: =deploy-model-write-file= now writes ='= before =prin1=.

*** Bug 3: Missing =--disable-debugger= and silent stderr in deploy script
=get_model_field= in =scripts/data-ui= did not pass
=--disable-debugger= to =ros run= (unlike =compile_default_model=).
=model_field= suppressed stderr with =2>/dev/null=, hiding errors.

Fix: Added =--disable-debugger= to =get_model_field=; removed
=2>/dev/null= from =model_field=.

Also fixed =compile_default_model= which used =(read in)= without
=cadr= — a pre-existing bug that meant the validation step was
silently compiling only the base model (nil types) instead of the
user's model.

*** Bug 4: sudo password prompt hangs background thread
The deploy script needs =sudo= for HAProxy configuration. When
running from a background thread inside SBCL, =sudo= opens
=/dev/tty= directly for password prompts, gets stopped by the
kernel (SIGTTIN or similar), and hangs forever.

Fix: Configured NOPASSWD sudoers rule
(=/etc/sudoers.d/data-ui-deploy=) for the HAProxy-related
commands. Note: the initial rule used =/bin/systemctl= but the
actual path on this system is =/usr/bin/systemctl= — =sudo=
matches on literal path strings, so this must be correct.

*** Result
Deploy from Model Bank button now works end-to-end: model
validation → file write → git commit → compile → k3d deploy →
HAProxy routing → live application. Confirmed working with
=modelbank.demo.data-ui.com=.

** DONE Admin password                  :model:frontend:backend:mvp:bug:
:PROPERTIES:
:CREATED: [2026-08-09 Sun]
:COMPLETED: [2026-08-09 Sun]
:END:
Deployed app admin password is invisible when deploying from Model Bank
When deploying via the Deploy Model button in Model Bank, the
generated admin password is not surfaced to the user. The deploy
succeeds and the app goes live, but the user has no way to log in
as admin.

The password is generated by =ensure_instance_secrets= in
=scripts/data-ui= and stored in
=~/.local/state/data-ui-deploy/<name>/secrets.env= as
=ADMIN_PASSWORD=<value>=. When deploying manually from the
shell, the script prints it to stdout. But when deploying via the
button, stdout is captured by =deploy-model-run-script= (in
=lisp/model.lisp=) and discarded on success — only used for
error messages on failure.

*** Possible approaches

1. *Embed in completion status* — =deploy-model-async= could parse
   the password from stdout (or read =secrets.env= directly) and
   pass it to =set-status= as something like
   ="complete: admin password is <pwd>"=. Simple but puts a
   password in a UI-visible status field.

2. *Dedicated "show credentials" button* — a second =:button=
   field on the model record that reads the password from the
   deploy state directory on demand. Cleaner UX, more work.

3. *Return in async result plist* — not feasible; the password
   isn't known when the hook returns =(:async t)=.

*** Relevant files

- =lisp/model.lisp= lines ~459-503 (=deploy-model-run-script=,
  =deploy-model-async=)
- =scripts/data-ui= (=ensure_instance_secrets=, =deploy= function)
- Deploy state: =~/.local/state/data-ui-deploy/<name>/secrets.env=

** DONE Multiple M2M per type                     :compiler:backend:mvp:bug:
:PROPERTIES:
:CREATED: [2026-08-09 Sun]
:COMPLETED: [2026-08-09 Sun]
:END:
When a type has more than one M2M joiner (e.g. =:chores= has both
=:chore-tags= and =:chore-users=), the compiler generates incorrect
insert SQL for each joiner. Each joiner's INSERT statement includes
columns from *all* joiners on the type, not just its own two FK
columns.

Example from the chores model (two joiners: =chore-tags= and
=:chore-users=):

#+begin_src
COMPLETED-BY → insert into rt_chore_users
  (chore_id, user_id, chore_id, tag_id) values ($1, $2, $3, $4)
TAGS         → insert into rt_chore_tags
  (chore_id, user_id, chore_id, tag_id) values ($1, $2, $3, $4)
#+end_src

Both statements have 4 columns — a union of all joiner FK columns.
Each should have only its own two (=chore_id, tag_id= for one;
=:chore_id, user_id= for the other). The param-key lists are also
merged (=CHORE-ID USER-ID CHORE-ID TAG-ID= for both).

This causes =be-insert= to fail with =NO-APPLICABLE-METHOD-ERROR=
on =rbac:get-id= because the backend tries to resolve values against
the wrong columns.

***** Key design decisions
1. *Phase A base SQL* (=SELECT id FROM <table>=) and *join SQL* (=SELECT DISTINCT id FROM <table> JOIN ...=) are generated at compile time, selected at runtime based on whether filters reference joined tables.

2. *=limit nil=* means "all rows" (no LIMIT clause). The default is 20. This preserves backward compat for =be-list-column=.

3. *Record reordering*: Phase B (hydration via =WHERE id IN (...)=) doesn't preserve Phase A's ORDER BY. Added =reorder-to-match= to restore the correct order after hydration.

4. *Count query* uses =COUNT(DISTINCT id)= when joins are present, =COUNT(*)= otherwise. Same WHERE predicates as the ID query.

5. *All query values parameterized* — LIMIT, OFFSET, and filter values all use =$N= bind parameters.

***** DONE 7a: Grain and measure shape                       :compiler:mvp:

How authors declare grain, measures, and join path. One grain + N

The hardest design question in the analytical path. Today a type's
fields aggregate over joins to /that type/ — Model Bank's
=:average-rating= is an avg over ratings joined to a model. But a
leaderboard needs a /different grain/: one row per /user/, with

original chores sketch).

***** DONE 7b: Read-only / rollup types                      :compiler:mvp:
:PROPERTIES:
:CREATED: [2026-08-09 Sun]
:COMPLETED: [2026-08-16 Sun]
:END:
=:table nil= (or equivalent), no create/update/delete, RBAC/display

A leaderboard is not a table — it is a computed view. This sub-item

dedicated read-only type keeps the separation clean.

** TODO Rating privacy and write permissions           :backend:model:
:PROPERTIES:
:CREATED: [2026-09-02 Wed]
:END:
Revisit Model Bank rating sanity. The modeling is right (own
=:ratings= table, write-through virtual field on =:models=), but
the entry point and role inheritance leave open issues:

- *Model owner can see who rated their model.* =execute-write-to='s
  insert path makes a new =:ratings= row inherit the source
  model's resource roles — including the creator's exclusive
  role — so the owner can read rater identities through the
  =:ratings= type. Rater identity should be the rater's business
  (and admin's), not the model owner's.
- *Users must not be able to alter other users' ratings* — neither
  via the =:ratings= type directly nor via write-through. The
  write-through upsert is keyed on model + user, so it should only
  ever touch the acting user's own row; verify every path, then
  enforce.
- *Rating currently requires model-update permission.* The rating
  write rides =be-update= on =:models=, inheriting the host row's
  type- and record-level update gate: a user who can't edit a
  model can't rate it, and a user who can edit it can change more
  than their rating. Likely direction: permission routing for
  pure write-through fields (gate on the /target/ table's update /
  create permission, skip the host-row update), not field-level
  RBAC. Same schema addition as the Role-gated Deploy button
  (per-field editability flags in the form JSON) would then make
  the stars editable while the rest of the form is read-only.
- One rating per (model, user) must hold on every path; the
  identity keys declare it, but nothing yet verifies it.

Privacy principle to decide deliberately: the aggregate
(=:average-rating=) is public; individual ratings and rater
identity are the rater's. Today that split is an accident of
resource-role propagation, not a decision.

** TODO =:hide-zero t= on rollup types                    :compiler:backend:
:PROPERTIES:
:CREATED: [2026-08-15 Sat]
:END:
Type-level opt-in that drops grain rows whose measures are empty
after aggregation. MVP keeps every grain row (zero-fact retention,
Issue 8). Leaderboards and plan 12's dead-models path (same rollup,
sort ASC) need those zeros.

Not a default flip: adding the flag later is additive; turning it
on by default would be a breaking change.

When set:
- Measure Phase A appends =HAVING= (typically
  =COUNT(<fact>.id) FILTER (...) > 0=). SUM/COUNT of no facts is
  0; AVG is NULL. "Zero" is not one predicate; pick the gate
  (usually the =:count=).
- =:total= must count only remaining rows. Today's
  =SELECT COUNT(*) FROM <grain>= becomes a lie. Spec seam is
  plan 08b Step 5.

Do not open a general HAVING DSL (thresholds, OR, "hide if all
measures empty"). One boolean.

=:hide-zero= on a non-rollup is a compile error. Absent is legal
(today's behavior).

** TODO =:weighted-score= derived measure         :compiler:backend:model:
:PROPERTIES:
:CREATED: [2026-08-15 Sat]
:END:

Bayesian / IMDB-style composite measure: blend an average and a
count into one sortable score so low-count items stop outranking
well-rated ones (one 5-star rating vs fifty ratings averaging
4.8). First instance of a /registered composite measure/ — a
registry entry over sibling measure fields with a parameter
schema (validates the model, drives the no-code palette, serves
as the AI spec). Not an expression DSL; no raw code in the model.

#+begin_src lisp
:score (:type :real
        :derived (:weighted-score
                   :avg-field :recent-avg
                   :count-field :recent-ratings
                   :prior 5)
        :sortable t)
#+end_src

Formula: =(v/(v+m))·R + (m/(v+m))·C= where v = the count field,
R = the avg field, m = author-declared =:prior= (positive), C =
grand mean of the same (filtered) facts the aggregates read —
computed once per request, bound as a parameter.

Semantics to freeze when specified:
- =COALESCE= around R inside the expression; SQL NULL must not
  propagate through the arithmetic
- Zero facts → score = C exactly (dead models sit at the prior,
  mid-board; still findable by ascending sort)
- =:avg-field= / =:count-field= must name sibling /measure/
  fields on the same rollup; compile error otherwise

Why post-MVP: it is a measure Phase A expression (sortable,
page-honest), so it needs items 08–10 green first; and where the
count is "distinct users that rated", it consumes the Issue 16
fan-out rules — a wrong count silently poisons the score. Named
consumers: Model Bank ranked by score instead of raw average.
Future curated formulas (time decay for "hot", Wilson lower
bound for "controversial") follow the same registered-measure
pattern.
